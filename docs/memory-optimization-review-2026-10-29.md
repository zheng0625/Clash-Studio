## 2. 已复现问题

### R1：连接缓存清理未受采样锁保护（高优先级）

位置：`server/runtime.py:272`、`:633`、`:728`、`:773`。

`connection_snapshot()` / `connection_json()` 持有 sample_lock；`_clear_connection_cache_locked()` 自身不取锁，应用、monitor 和停止路径却直接调用它，只持 lifecycle_lock。实现报告称这些路径遵守 `lifecycle_lock → sample_lock → client_lock`，与实际代码不符。

本轮用临时目录、假进程和假连接响应，在 connection_json 最后一次存活检查得到 True 后设置线程屏障，让另一线程执行 `_stop_locked(final_sample=False, report=False)`，再继续编码。结果：

```json
{"case":"stop_during_connection_json","body":"null","wire_repopulated_after_stop":true,"sample_released":true}
```

这是确定性交错注入，证明存在该调度下的错误，不代表每次停止都会触发。连接接口应返回对象，此时却返回 JSON null，停止后编码缓存又被填回。现有 lifecycle 测试只验证串行停止，未覆盖该交错。

建议统一清理时的 sample_lock 所有权，并补停止/编码并发测试；修复时保持既定锁序，不能简单给整个采样路径反向加 lifecycle_lock。

### R2：全局 300 张卡片预算不成立

位置：`frontend/src/ProxyPanel.vue:32`。

页长公式保留最低 20 项；展开组数超过 15 后，总数继续增长。本轮执行真实组件 script setup 的计算逻辑，使用 16 个展开组、每组 100 个成员：

```json
{"case":"global_proxy_budget","groups":16,"per_group":20,"total":320,"budget":300}
```

模板对每个展开组渲染 groupPage，故该计算直接决定卡片数量；本轮没有用浏览器实测 DOM。30 组同样会达到 600 项。现有测试只覆盖 2 组和 6 组，未触达下限分支。

建议让组数与全局预算共同受限，或制定总和严格不超过预算的分配策略；同步校正 CHANGELOG 和实现报告中的绝对上限表述。

### R3：缓存有并发上限，没有等待队列上限

位置：`server/cache.py:75`、`:79`、`:91`。

max_keys 只限制 pending 字典；超出后进入 bypass，再阻塞等待同一个 BoundedSemaphore。同键 Future 等待也没有本地超时、取消或人数上限。实际正在执行的 build 有界，但缓存自身不限制阻塞调用数，仍依赖外层线程池或请求调度器。

本轮配置 max_builds=1、max_keys=1，阻塞首个构建后提交 11 个不同键：

```json
{"submitted":12,"unfinished":12,"in_flight":1,"bypass":11,"waiters":0,"max_waiters":0}
```

11 个旁路请求全部仍在等待，但 waiters 统计为 0。不能把该实现写成“限制等待队列”。建议明确准入/等待预算、超时和取消语义，并统计信号量等待者。

### R4：编辑器卸载后会继续调度待处理预览

位置：`frontend/src/ConfigEditor.vue:73`、`:118`。

卸载只清除当时的 timer，没有 disposed 标记，也不清除 previewPending。若已有预览请求在途并积累了下一次预览，卸载后第一请求完成，finally 仍创建新 timer，再发一次 API 请求。

本轮执行组件真实脚本、收集并调用其 onUnmounted 回调：先修改草稿，启动一次阻塞预览，再请求一次预览形成 pending；卸载后释放第一请求，执行新创建的 timer，结果：

```json
{"case":"preview_after_unmount","timers_created_after_unmount":1,"api_calls":2}
```

建议卸载时使代次失效并清空 pending，禁止后续调度和结果写入；能否取消传输另按 API 支持处理。现有前端测试将 onUnmounted 替换为空函数，dispose 只停止 effectScope，因此不能发现此问题。

## 3. 交付与测量缺口

1. **检查点不能单独还原优化前源码。** `artifacts/memory/checkpoint-20261029/` 只有 README 和 SHA256SUMS。162 文件清单及其 SHA-256 与报告一致，但没有源码内容、补丁或对应提交；当前已有 13 个清单内文件与原哈希不同。因此它能证明文件指纹，无法据此重建优化前的脏工作区。父提交 `0989c1b` 也不能补齐当时未跟踪源码。需要补可还原的基线来源，不能将当前候选重新保存后称作优化前基线。
2. **采样器尚不能支持完整验收口径。** `measure-memory.ps1` 只遍历父子树，未补录提权助手下的树外受管理内核；只保存 PID，没有创建时间，无法抵御 PID 复用；只分 interface/service/core/other，不能独立归因主/测速内核和宿主/WebView。它将各进程中位数/p95 相加，不能代表同一时刻角色总量的中位数/p95，虽然 summary.note 已提示部分差异。采样期间流式写文件，但结束时 Import-Csv 将全部数据读回内存，未实现全流程有界处理。
3. **缺独立浏览器验收。** 当前 `frontend/tests/memory-frontend.cjs` 执行组件 script setup 和 Vue 响应式，但不挂载模板，生命周期与 document 被替身覆盖；不能证明真实 DOM 卸载、detached DOM、监听器释放或 retained heap 收敛。原任务 E 的 `scripts/verify-memory-ui.cjs` 与 `docs/memory-validation-2026-10-29.md` 在复核时均不存在。本文件是源码与测试复核，不替代该实机终验。
4. **缺完整性能实验。** Windows Release S0–S7、三次独立启动、预热/稳定窗口、集成 A/B、30 轮堆对比、60 分钟稳定性、CPU 与交互 p95 均没有完整证据。500/20,000 连接、2,000 节点/30,000 规则压力也未覆盖；现有合成连接样本为 5,000。
5. **缺本轮平台验收。** 当前 Windows 环境中的 pytest 和前端构建不等于 Linux/Android 平台回归；原生隐藏恢复、VPN/TUN/DNS、系统代理恢复均不能由这些测试替代。Linux RssAnon 也不能解释成 Windows 私有提交，UI 统一“私有提交合计”的文案仍需按平台处理。

## 5. 后续优先级

1. 先修复 R1，并覆盖停止、退出、应用与连接读取并发。
2. 修复 R2、R4；补充超过 15 组和卸载时在途预览用例；完善 R3 的等待预算与统计。
3. 校正“全部有上限”“等待有界”“M01–M07 完成”等过强表述；保留已完成与未验证的区别。
4. 补可还原源码基线和正确的进程采样统计，再做受控 Release S0–S7 与真实浏览器生命周期/堆验收。
5. 依据测量结果决定是否继续 M08–M11、摘要拆分或连接分页；它们是后续工作，不应为凑完成数量盲目实施。

最终建议：**保留已有实现，优先修复已复现缺陷并补齐测量证据；当前状态为“部分实现、基础回归通过、性能验收未完成”。不能声称客户端总内存下降某个百分比，或已达到 20% 目标。**
