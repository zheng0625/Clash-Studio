# Clash Studio 运行时 RAM 深度优化方案

日期：2026-10-29。状态：待实施的专项方案；本次仅交付文档，不代表轻量模式、服务拆分或内存目标已经完成。

目标：显著降低长期后台代理的常驻内存，同时保留主内核连续运行、托盘操作、订阅更新、配置编辑与可靠退出。Windows 桌面优先，Linux 单独验收；Android 不纳入桌面窗口销毁及服务拆分策略。

## 2. “几十 MB”如何对标

用户观察到 Clash Verge 占用几十 MB，但其版本、窗口状态、统计字段和进程范围尚未确认。该数字作为对标线索，不直接作为验收基线，也不据此承诺 Clash Studio 的全进程总量能达到同一水平。

Clash Verge Rev 当前主分支的 `entry_lightweight_mode()` 会调用 `destroy_main_window()`；窗口管理代码调用 `window.destroy()`，再次打开时支持重建窗口。可借鉴的是窗口生命周期设计，实际内存收益仍需同环境测量。[轻量模式源码](https://github.com/clash-verge-rev/clash-verge-rev/blob/main/src-tauri/src/core/lightweight.rs)、[窗口管理源码](https://github.com/clash-verge-rev/clash-verge-rev/blob/main/src-tauri/src/utils/window_manager.rs)。实施时应固定参考提交，避免把变化中的主分支当成稳定契约。

对比必须同时给出：

| 范围 | 包含什么 | 用途 |
| --- | --- | --- |
| 宿主 | Rust 主进程 | 解释任务管理器单行数值 |
| 界面 | 主窗口、托盘及关联 WebView 进程 | 测量窗口释放收益 |
| 服务 | Python 配置服务与相关辅助进程 | 测量服务按需启动收益 |
| 内核 | 主 Mihomo、测速 Mihomo，分别列出 | 避免漏算临时内核 |
| 合计 | 本实例所有确认归属的进程及权限助手，去重 | 面向用户的整体成本 |

Windows 工作集和私有提交量分别报告；工作集含共享页，跨进程求和会重复计入部分共享内存。私有提交量不是实际驻留 RAM。Linux RSS、PSS、RssAnon 不冒充 Windows 私有提交量。GPU 内存单独报告，不混入 CPU RAM 合计。[Windows 指标定义](https://learn.microsoft.com/en-us/windows/win32/api/psapi/ns-psapi-process_memory_counters_ex)

## 3. 当前源码中的关键约束

| 位置 | 已确认的当前行为 | 改造要求 |
| --- | --- | --- |
| `src-tauri/src/desktop.rs`：`close_desktop()` | 驻留关闭调用 `window.hide()` | 增加可选的延时销毁路径，保留普通隐藏模式 |
| 同文件：`show()` | 只显示已经存在的主窗口 | 必须支持不存在时创建，合并重复打开请求 |
| 同文件：`show_menu()/hide_menu()` | 自定义托盘 WebView 按需创建、隐藏后保留 | 轻量模式改用原生菜单并释放托盘 WebView |
| 同文件：`DesktopState.ready`、退出菜单 | 前端 ready 与退出消息相关联 | 销毁后复位 ready；无窗口时可完整退出 |
| `src-tauri/src/main.rs`：setup | 后台启动仍创建主窗口，只将 visible 设为 false | 静默轻量启动应跳过创建，而非创建后立刻销毁 |
| 同文件：`Startup/Backend/BackendJob` | 启动并持有 Python；停止时请求后端清理；Windows Job 负责进程回收 | Python 可重启后需更换单次启动模型，并重新明确进程所有权 |
| `server/api.py`：cleanup/lifespan | Python 退出会恢复代理、停止内核、关闭助手 | 未拆分前绝不能把退出 Python 当作空闲回收 |
| `server/job.py` | 内核 Job 有关闭时杀进程语义 | 配置 worker 不得拥有长期内核的 Job |
| `vendor/app/main.py`：schedule/lifespan | Python 执行订阅定时更新；服务提供订阅相关接口 | worker 退出后仍需有调度和服务承接者 |
| `frontend/src/Client.vue`：关闭/退出与输入保护 | 前端检查未保存输入并处理关闭确认 | 原生销毁前需要可靠握手，不能绕过保护 |

这些函数会继续随其他工作变化，实施时以函数职责而非固定行号定位。

## 4. 两个可以独立交付的目标架构

### 4.1 第一阶段：窗口轻量化，Python 暂时常驻

| 状态 | Rust/原生托盘 | Python | 主 Mihomo | 主/托盘 WebView |
| --- | --- | --- | --- | --- |
| 正常前台 | 保留 | 保留 | 按用户启动状态 | 主窗口存在 |
| 短时间隐藏 | 保留 | 保留 | 不变 | 主窗口暂时保留 |
| 后台轻量 | 保留 | 保留 | 不变 | 主窗口销毁；托盘使用原生菜单 |
| 再次打开 | 保留 | 保留 | 不变 | 创建主窗口并读取最新状态 |

该阶段不迁移内核控制，范围较小，可独立测量收益。销毁 WebView 不保证所有浏览器共享进程立即退出；必须观测对象释放、相关进程及内存，不强杀 WebView 进程制造低占用。

### 4.2 第二阶段：配置服务按需启动

| 职责 | 最终负责人 | 是否常驻 |
| --- | --- | --- |
| 系统托盘、窗口、全局退出、单实例入口 | Rust 宿主 | 是 |
| 主内核启动/停止/监控、控制鉴权、系统代理恢复、权限助手协调 | Rust 运行管理层及必要的原生助手 | 是 |
| 配置解析、编辑预览、合成、导入/订阅刷新 | Python 配置 worker | 有任务时运行 |
| 定时订阅/GeoData 等任务的触发、重试与任务状态 | Rust 调度层；重任务交给 worker | 调度常驻，worker 按需 |
| 发布配置、编辑版本及持久数据 | 原有持久存储，写入所有权明确 | 数据持久化，不靠 worker 活着保存 |
| 本地订阅分享 HTTP 等长期访问能力 | 原生端点承接；未迁移前保留 Python 租约 | 按功能需求 |
| 代理转发、DNS、规则匹配 | Mihomo | 按用户启动状态 |

只启动界面不一定启动 Python：基础状态/托盘/内核操作迁移后由 Rust 提供；打开工作台、刷新订阅等需要配置能力时才唤起 worker。迁移过程中允许基础界面仍唤起 Python，不提前宣称完全按需。

第二阶段验收前，第一阶段可以先交付。不要求为省内存一次性重写全部配置编辑功能。

## 5. P0：冻结可复现基线与生命周期契约

1. 保存当前源码内容、父提交、锁文件、构建参数与文件哈希；只有哈希清单而无可还原源码不算可复现检查点。包含相关未跟踪源码，排除用户配置与凭据。
2. 基于当前实现构建 Release 基线。已有开发后端冒烟或脚本内部模拟对照只作参考，不替代客户端 A/B。
3. 重新核验复核报告中的 R1–R4；与窗口销毁直接相关的编辑器卸载回调、监听器清理及旧响应处理必须先修复。
4. 固定主窗口创建、隐藏、销毁、恢复、退出五类操作的负责人和状态字段；同一轮只允许一个 agent 改 `desktop.rs/main.rs` 生命周期。
5. 完成现有后台能力清单：订阅定时刷新、订阅分享服务、GeoData 下载、日志、测速、UAC、TUN、系统代理、配置应用回滚。每项登记是否阻止销毁窗口、是否阻止退出 worker。

## 6. P1：可选后台轻量模式

### 6.1 状态机

原生管理器作为唯一状态来源，建议状态：`Visible → HiddenWarm → Preparing → Lightweight → Restoring → Visible`，另有 `Quitting`。名称是设计建议，不是当前已有 API。

| 事件 | 必须执行的行为 |
| --- | --- |
| 用户关闭窗口且开启驻留 | 沿用未保存输入确认；隐藏并启动轻量倒计时 |
| 窗口最小化 | 第一版只暂停不必要采样，不自动销毁；避免改变任务栏恢复语义 |
| 倒计时到期 | 校验当前窗口代次、可见性、输入状态和任务阻塞项，发起销毁准备握手 |
| 准备成功 | 原生切换托盘菜单，释放托盘 WebView，再销毁主窗口；确认销毁结果后标为 Lightweight |
| 输入未保存、状态未知、握手超时或销毁失败 | 保留窗口及数据，仍处于隐藏状态；不强行销毁，不自动保存发布 |
| 倒计时/准备期间重新打开 | 递增代次并取消准备，旧 ack 不得触发销毁 |
| 轻量状态打开/重复启动应用 | 合并为一次创建，注入原语言及数据目录配置，注册新窗口监听器 |
| 恢复成功 | 获取最新 runtime/session/revision，再恢复页面选择与视图；旧事件不当作最新状态 |
| 恢复失败 | 保留代理；原生菜单提供重试和退出，显示失败原因，不无限重建 |
| 显式退出 | 抢占恢复/创建任务，执行现有完整退出清理，不重新创建窗口来完成退出 |

必须处理最后一个窗口销毁时的 Tauri 退出行为。按锁定版本实现仅在驻留且非 Quitting 时阻止自动退出；不能一概拦截所有退出事件。窗口销毁与应用退出是不同操作，前者不得调用 `Startup.stop()`。

### 6.2 未保存输入与恢复数据

- 建议新增 `prepare_lightweight(generation)` / ack 契约，包含窗口代次、是否允许销毁、阻塞原因和视图状态版本；前端冻结短暂的变更入口，完成异步清理后回复。建议准备超时 3 秒，超时保留窗口。
- 汇总所有输入来源：配置 edits、元信息、网络/端口、模块、导入文本、外观裁切与弹窗。不能只检查单个 `editorDirty`。
- 未保存数据存在时自动轻量化延期。手动进入时沿用明确的保存/放弃/取消流程；不静默丢弃、不默认保存。
- 首轮只恢复轻量视图状态：页面、所选订阅 ID、筛选、页码、展开组、滚动位置及主题偏好。做 schema/version 校验，数据已删除时回到可用页面。
- 用户主动保留的连接暂停快照或未完成的详情操作，首轮作为销毁阻塞项；后续若支持快照持久化，需独立设计大小上限、隐私和失效说明，不能无声转换为实时状态。
- 预览在途但内容未保存时不销毁；后台已提交且可按 operation_id 恢复的任务可继续。原生/后端保存任务结果，窗口回来主动查询，不能只依赖事件推送。
- 新窗口有新的 generation，`desktop_ready` 必须带身份或等效校验；销毁时立即复位旧 ready 和监听器引用，迟到的旧 ready 不得污染新窗口。

### 6.3 偏好与用户体验

建议实验配置：`lightweight_enabled=false`、`lightweight_delay_seconds=120`，允许手动进入。该默认值用于灰度验证，尚未写入产品；通过验收后再决定是否默认启用。

静默启动且启用轻量模式时跳过主 WebView 创建。只保留现有“登录自启不自动启动代理”的行为，不借此改变内核启动策略。

失败时降级为原有隐藏模式；不清空 WebView 数据目录、不重置用户偏好。只有真实测量支持时才改变延迟和默认策略。

## 7. P2：原生托盘与后台请求收敛

现有代码已有 Tauri 原生 Menu/CheckMenuItem/Submenu，可以先复用其菜单状态与动作，避免另建一套业务逻辑。注意右键事件目前还会调用自定义 `show_menu()`，切换原生菜单后必须关闭这一路，防止双菜单和隐式重建 WebView。

- 轻量状态只使用原生菜单，覆盖打开、内核状态、启停、规则/全局/直连、系统代理/TUN、轻量状态和退出；busy/错误/语言变化仍正确显示。
- 普通模式可继续自定义托盘；进入轻量状态销毁 `tray-menu`，退出轻量时按用户操作重新创建，不能恢复主窗口时顺手创建托盘 WebView。
- UI 连接/曲线/内存轮询停止；Python 保留阶段，原生托盘仍可查询必要摘要。先保留已有同步时效，测量后再决定退避频率，不能静默漏掉内核异常退出。
- 后台操作失败优先显示原生通知或菜单状态；需要交互时才恢复主窗口，防止错误轮询反复唤起界面。
- Linux 托盘行为单独验证；原生菜单不可用时保留可恢复的现有路径，该环境不得宣称“后台无托盘 WebView”。

P1/P2 应作为一个可独立验收的交付包：主内核与 Python 生命周期不变，重点证明界面资源释放及可靠恢复。

## 8. P3：Python 按需启动的前置拆分

### 8.1 迁移顺序

1. **抽取配置 worker 边界。** 分离配置解析/合成/预览与 Runtime/权限/代理副作用。配置 worker 不创建主内核、系统代理或管理员助手。
2. **迁移运行管理。** Rust 接管主内核的唯一所有权、运行状态、控制 API、进程监控、日志排空、停止/失败恢复；管理员助手协议与代理恢复责任同步迁移。迁移不是让 Python 和 Rust 同时控制一个内核。
3. **迁移后台调度及长期开启的服务。** Rust 保存下次触发时间、任务 ID、重试状态，按需唤起 worker；本地订阅分享端点未迁移时持有服务租约，禁止空闲退出。
4. **迁移退出与异常处理。** 将“退出配置 worker”与“停止整个应用”分开。只有全局退出才停止主内核并恢复代理；worker 正常/异常退出均不执行全局清理。
5. **启用按需回收。** 前述步骤和故障测试全部通过后，才开启 worker idle timeout。

### 8.2 配置事务与权限边界

- worker 输出候选配置、校验结果和对应 profile/workspace revision；Rust 校验版本与任务代次，原子发布后应用。保存与应用是不同事务，保留现有语义及错误说明。
- 应用失败时使用受控的上一份有效配置回滚；回滚材料保存在持久层，不依赖已退出 worker 的内存。不能因为降低内存删除必要历史。
- 首版只允许一个写配置的 worker；Rust 调度层不直接并发写原 SQLite 数据。先明确唯一写入者和跨进程版本冲突协议，再考虑迁移存储实现。
- Windows 主内核/助手由长期宿主对应 Job 管理，worker 有独立 Job。验证关闭 worker 句柄不会结束主内核，父进程异常退出仍按既定策略清理，不能靠随意脱离 Job 留下无人管理内核。
- 保留本机接口认证、路径白名单与数据目录隔离；worker 重启后更新端点和凭据，不将真实令牌写入日志或前端持久存储。
- 定时刷新结果不自动变成新的生效配置，是否应用遵循当前产品语义。订阅刷新、GeoData、测速等任务要有互斥与恢复记录，避免服务休眠造成漏执行或重复执行。

### 8.3 worker 生命周期协议

建议状态：`Stopped → Starting → Ready → Draining → Stopped`，失败进入 `Failed` 并支持受控重试。原 `Startup` 单次完成结果不能直接作为可重启 worker 管理器使用。

| 机制 | 要求 |
| --- | --- |
| 启动合并 | 并发请求共享一次启动，启动失败唤醒全部等待者；队列、超时和内存预算有上限 |
| 任务租约 | 在途编辑/导入/刷新/下载持有 lease，完成或失败释放；空闲判断以任务引用计数为准 |
| 空闲回收 | 初始实验 TTL 60 秒，与 30/120 秒做 A/B；无任务且无长期服务 lease 才进入 Draining |
| 排空竞态 | Draining 期间新请求按协议取消排空或等待下次启动；不能丢失已接收任务 |
| 会话代次 | 每次启动产生 worker generation；旧响应不能回写新会话状态 |
| 幂等与错误 | 只读请求可受控重试；写入请求有 operation_id 和持久结果查询，禁止遇超时就盲目重放 |
| 故障隔离 | 杀掉配置 worker 不应改变主内核 PID、现有连接或代理设置；编辑端明确报错并可恢复 |
| 版本兼容 | 握手验证协议版本/能力，旧包不匹配时返回可诊断错误，不将空响应当成功 |

接口字段和状态名称是提案，实施前由单一契约负责人冻结。不能用暂停 Python 线程或操作系统挂起进程代替职责拆分，这会冻结代理控制、请求和定时任务。

## 9. 性能实验、目标与退出条件

### 9.1 对比构建

| 构建 | 内容 | 目的 |
| --- | --- | --- |
| B0 | 当前第一轮修复后、未启用本专项的 Release | 真实对照 |
| B1 | P1/P2 主窗口销毁与原生托盘，Python 常驻 | 单独测界面释放收益 |
| B2 | P3 worker 按需运行，其余与 B1 相同 | 单独测 Python 常驻成本 |

使用同机器、同窗口尺寸与主题、同订阅/规则库/内核、同代理/TUN 状态和可重复负载。每种至少三次独立启动。开 DevTools 的堆分析与关 DevTools 的进程测量分开进行。

场景：冷启动前台；关闭至轻量后稳定 5 分钟；后台 60 分钟；开关窗口 30 轮；托盘菜单开关 30 轮；有草稿/预览/导入/保存/UAC 时进入轻量；worker 并发启动、排空、异常退出；静默启动；无界面时退出。销毁后至少观察 30/60/120 秒三个时间点，不挑最低瞬时数值。

持续测试流量记录连接 ID、主内核 PID 和应用连续性，背景窗口动作不应重启内核或导致已有测试连接断开。系统代理/TUN 真实验证使用独立测试环境，mock 结果单独列出。

### 9.2 建议门槛（基线后冻结，非已实现结果）

- B1：以“非主内核进程私有提交量”作为诊断指标，目标较 B0 同状态稳定中位数下降至少 25%；同时公布工作集和全进程总量，不能隐去主内核或共享进程。若基线证明该门槛不适用，实施前记录调整依据。
- B2：在无后台任务/长服务 lease 时，TTL 到期后无配置 worker 进程；减少的真实 RAM 由 A/B 数据决定，不预填固定 MB。若 Python 长期无法退出，报告哪个功能持有 lease。
- 恢复体验：B1 从打开动作至可交互 p95 建议不超过 2 秒，B2 依赖 worker 的编辑器冷打开 p95 建议不超过 3 秒。无网络依赖的本地响应与远程订阅下载分别计时；超时必须有可见反馈。
- 前台正常状态不得因本专项明显增大：建议内存中位数增加不超过 `max(5%, 10 MiB)`；同时报告 CPU 和操作延迟，不以卡顿换低内存。
- 30 轮后无重复主窗口、悬挂监听器和不断增长的进程数；60 分钟稳定窗口无不能解释的持续增长。既有草稿、编辑结果和暂停状态必须符合前述阻塞/恢复规则。
- 代理、TUN、DNS 防泄漏、严格出口审查、节点选择、失败回滚和退出恢复全部通过；任何数据丢失或代理生命周期回归均阻断合并。

“几十 MB”不作为未测量的整机硬指标。最终报告必须回答：哪个模式、哪些进程、什么配置、什么统计字段达到多少 MB，恢复代价是多少。

## 11. 回退与完成标准

- P1/P2 首轮由偏好开关控制。关闭后恢复普通隐藏和既有托盘行为，已进入轻量状态时先按正常恢复路径创建窗口；失败可使用原生菜单退出。
